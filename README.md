## Цель работы

Разработать два небольших веб-сервиса и связать их через Apache Kafka. Развернуть систему с помощью Docker Compose, изучить распределение сообщений между партициями и потребителями, проверить сохранность заказов при остановке сборщиков, настроить время хранения сообщений и организовать мониторинг.

## 1. Устройство проекта

В работе смоделирован интернет-магазин с отдельным сервисом создания заказов и сервисом их сборки. Пользователь выбирает товары и создаёт заказ, после чего `user-service` публикует событие в Kafka. `picker-service` читает сообщения из топика `orders`, имитирует сборку товара и показывает результат на своей странице.

```text
Покупатель / браузер
         |
         v
    user-service                  (Producer)
         |
         | событие order_created
         v
     Kafka / orders               (топик из 4 партиций)
         |
         v
     picker-group                 (Consumer Group)
       /     \
      v       v
  picker-1  picker-2              (Consumers)
```

## 2. Разработка сервисов

### 2.1. Сервис пользователя (`user-service`)

Была создана страница выбора товаров с кнопкой **«Создать заказ»**. После нажатия сервис формирует сообщение JSON с уникальным `order_id`, списком товаров и временем создания. Продюсер отправляет его в топик `orders`. После подтверждения Kafka на странице отображаются **партиция** и **offset**, по которым можно найти конкретный заказ.

`order_id` используется также как ключ сообщения в Kafka. История отправленных заказов выводится в таблице веб-интерфейса.

## 3. Развёртывание Kafka и сервисов

Kafka была поднята в Docker в режиме **KRaft**: один узел выполняет роли брокера и контроллера. Топик `orders` создаётся и настраивается при запуске контейнера `topic-init`, который использует Kafka Admin API и параметры из `docker-compose.yml`.

Основные настройки учебной конфигурации:

| Параметр | Значение | Назначение |
|---|---|---|
| Топик | `orders` | События о созданных заказах |
| Начальное число партиций | `2` | Исходная конфигурация до экспериментов |
| Число партиций после масштабирования | `4` | Проверка параллельной обработки |
| Consumer Group | `picker-group` | Совместная обработка заказов сборщиками |
| Replication factor | `1` | Один учебный брокер |
| Обычный срок хранения | `604800000` мс (7 дней) | Retention сообщений |
| Способ управления | `docker compose` + `topic-init` | Изменения через конфигурацию |

Для проверки были созданы несколько заказов. Оба сервиса показывали одинаковые `order_id`, `partition` и `offset`, следовательно, сообщения действительно передавались через Kafka, а не напрямую между сайтами.

## 4. Бизнес-ситуации: масштабирование и отказ

### 4.1. Подготовка к распродаже: увеличение числа партиций

**Проблема.** Перед распродажей ожидается рост количества заказов. При малом числе партиций невозможно подключить достаточное количество параллельно работающих потребителей внутри одной группы.

**Что изменено.** В конфигурации `topic-init` параметр `TOPIC_PARTITIONS` изменён с `2` на `4`, после чего конфигурация применена повторно. Kafka успешно увеличила число партиций существующего топика `orders` до четырёх.

![Топик с четырьмя партициями](<screenshots/3.1_4партиции.png>)

*Рисунок 3 — Результат увеличения количества партиций топика `orders` до четырёх.*

**Результат.** Появилась возможность распределять чтение между четырьмя потребителями одной группы. При попытке вернуться с четырёх партиций к двум выяснилось, что Kafka не поддерживает уменьшение количества партиций существующего топика обычным изменением конфигурации. Для такого перехода потребовалось бы создать новый топик и перенести в него данные. Поэтому фактически в ходе последующих экспериментов использовались **4 партиции**.

### 4.2. Добавление сборщиков и проверка распределения нагрузки

**Проблема.** Один экземпляр сборщика может не успевать обрабатывать поступающие заказы.

**Что изменено.** Запущен второй экземпляр `picker-service` с именем `picker-2`. Оба экземпляра подключены к **одной** группе `picker-group`. Веб-страницы доступны на разных локальных портах, но читают общий топик.

![Два экземпляра сборщика](<screenshots/3.2_два сборщика.png>)

*Рисунок 4 — Два экземпляра сервиса сборки, работающие с одной группой потребителей.*

![Проверка первых двух сборщиков](<screenshots/3.2_сборщик 1-2 чек.png>)

*Рисунок 5 — Заказы распределяются между `picker-1` и `picker-2`. В одном из наблюдений первый сборщик обработал 24 заказа, второй — 11; равномерного распределения по числу заказов Kafka не гарантирует.*

**Почему так работает.** Kafka назначает партиции участникам группы потребителей. В рассматриваемом эксперименте первый сборщик читал партиции 0 и 1, а второй — 2 и 3. При присоединении нового участника выполняется **rebalance**, то есть перераспределение назначений.

Затем для проверки ограничения параллелизма количество сборщиков было увеличено до **пяти** при **четырёх партициях**. У каждого экземпляра было своё имя, но одна общая группа потребителей.

![Проверка третьего и четвёртого сборщиков](<screenshots/3.2_сборщик3-4 чек.png>)

*Рисунок 6 — Проверка работы дополнительных экземпляров сборщика.*

![Проверка пятого сборщика](<screenshots/3.2_сборщик5 чек.png>)

*Рисунок 7 — Проверка поведения пятого сборщика при четырёх партициях.*

**Вывод.** В рамках одной Consumer Group одной партиции соответствует не более одного назначенного потребителя. Поэтому при четырёх партициях и пяти сборщиках **один сборщик не получает партиций и простаивает**. Добавление потребителей сверх количества партиций само по себе не увеличивает параллельность чтения.

По завершении проверки дополнительные сборщики были убраны из конфигурации; для дальнейших экспериментов использовались `picker-1` и `picker-2`.

### 4.3. Сборщик упал во время деплоя

**Проблема.** Во время обновления приложения сборщик может временно отключиться, но новые заказы продолжат поступать.

**Ход эксперимента.** Были остановлены оба экземпляра сборщика, при этом брокер Kafka и сервис пользователя остались работающими. Через сайт были созданы новые заказы. Затем `picker-1` был запущен снова и начал обрабатывать накопившиеся сообщения.

## 7. Мониторинг

### 7.1. Настройка сбора метрик

**Kafka Exporter** предоставляет метрики по брокерам, топикам, партициям и группам потребителей. **Prometheus** собирает эти данные через HTTP с заданным интервалом, а **Grafana** строит на их основе панели и графики.

![Подключение Prometheus](<screenshots/6_прометеус_подкл.png>)

*Рисунок 23 — Проверка подключения экспортера и получения метрик в Prometheus.*

![Метрика количества сборщиков в Prometheus](<screenshots/6_сум_сборщиков_прометеус.png>)

*Рисунок 24 — Проверка метрики участников группы `picker-group` в Prometheus.*

На дашборде Grafana созданы следующие панели:

| Панель | PromQL | Вид |
|---|---|---|
| Количество брокеров | `kafka_brokers` | Stat |
| Количество партиций | `kafka_topic_partitions{topic="orders"}` | Stat |
| Активные сборщики | `kafka_consumergroup_members{consumergroup="picker-group"}` | Stat |
| Consumer Lag | `sum(kafka_consumergroup_lag{consumergroup="picker-group",topic="orders"})` | Time series |
| Текущие offset по партициям | `kafka_topic_partition_current_offset{topic="orders"}` | Time series |
| Число сохраняемых сообщений (оценка) | `sum(kafka_topic_partition_current_offset{topic="orders"} - kafka_topic_partition_oldest_offset{topic="orders"})` | Stat |

Для временных графиков использован режим запроса **Range**, а для текущих числовых показателей — **Instant**. Разница между конечным и начальным offset даёт оценку числа записей для нашей конфигурации топика без compaction.

### 7.3. Метрики, по которым можно настроить алерты

Для учебной системы выбраны три основных сигнала:

| Метрика | Пример условия алерта | Что обнаруживает и чем грозит |
|---|---|---|
| `kafka_brokers` | Меньше `1` | Брокер недоступен; сервисы могут перестать передавать и получать заказы. При полном отказе экспортера метрика может отсутствовать, поэтому в реальной системе дополнительно проверяют `up`/`absent`. |
| `kafka_consumergroup_lag` | Суммарный lag больше `10` в течение минуты | Потребители не успевают за новыми заказами; увеличивается время ожидания сборки. Порог выбран для демонстрации. |
| `kafka_consumergroup_members` | Число членов группы меньше `1` | Все сборщики отключились; новые заказы остаются в Kafka без обработки. Нужно учитывать и отсутствие самой метрики. |

Эти условия предложены как **правила для алертов**; создание и отправка уведомлений в рамках эксперимента не проверялись. В рабочей системе пороги подбираются исходя из реального потока заказов и допустимого времени обработки.

## 8. Возникшие проблемы и их решение

В ходе работы возникло несколько ситуаций, которые помогли лучше разобраться в работе Kafka и Docker.

**Ошибка доступа к данным Kafka.** При первом запуске брокер завершался с `Exited (1)`. В логах была ошибка:

```text
java.nio.file.AccessDeniedException:
/tmp/kraft-combined-logs/bootstrap.checkpoint.tmp
```

Причина заключалась в правах на Docker volume: контейнер Kafka работал от пользователя с UID `1000` и не мог записать служебные файлы KRaft. После изменения владельца каталога тома и повторного запуска брокер заработал.

**`topic-init` не мог подключиться к Kafka.** В его логах появлялись сообщения `Failed to resolve 'kafka:19092'` и `RuntimeError: Kafka не запустилась`. Это оказалось следствием падения основного контейнера Kafka. После устранения проблемы с правами `topic-init` создал топик `orders` и применил конфигурацию.

**Не получилось уменьшить количество партиций с 4 до 2.** Изменение параметра в Docker Compose не уменьшило существующий топик. Это ограничение Kafka, а не ошибка скрипта: число партиций можно увеличить, но штатно уменьшить нельзя.

**В Kafka UI не удалось выбрать `segment.ms` в Custom Parameter.** Для эксперимента с retention был использован доступный параметр `retention.ms = 60000` при политике `delete`. Этого оказалось достаточно: число сообщений в топике уменьшилось со 107 до 4.
